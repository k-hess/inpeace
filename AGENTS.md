# Working in this repo

Instructions for AI coding agents (Claude, ChatGPT/Codex, Cursor, etc.) and anyone new to the codebase. Read this before changing anything. `README.md` has the overview and how to run it; `docs/` has the research and the plan.

## What this is

In Peace is a client-only prototype: a short intake, then a generated plan for someone settling a death or getting a family's affairs in order. No backend, no accounts, no network calls at runtime except optional PostHog analytics (currently off, key blank). All state is in `localStorage`.

Stack: Bun, TanStack Start (React 19, file routes, every route `ssr: false`), Tailwind 4, shadcn/ui, TypeScript strict. Deployed as static assets on Cloudflare Workers.

## Commands

```bash
bun install
bun run dev          # localhost:3000
bun run typecheck    # run this after every change; there are no tests
bun run build        # must succeed before anything is considered done
```

Use `bun`, never npm/yarn/pnpm. Add shadcn components with `bunx --bun shadcn@latest add <name>`.

## How the plan engine works

A `Rule` (see `src/data/states/types.ts`) has:

- `id`, unique, prefixed by state or `common-`
- `phase`: `"this-week" | "this-month" | "months-ahead"`
- `trigger(answers)`: returns true if the rule applies to these intake answers
- `copy(ctx)`: returns `{ title, body }`; `ctx` includes the answers, the date of death as a `Date`, and the state
- optional `computeDate(ctx)`: a real deadline, which surfaces the task in the "Right now" block when it's near
- optional `closing: true`: a reassurance card that sorts to the end of its phase

`buildPlan` collects every rule from `commonPacingRules` plus the chosen state's `rules`, keeps the ones whose trigger fires, groups by phase, and attaches the other sections (can-wait items, protection cards, liabilities, edge cases, people, paperwork, inventory). Adding a state means a new file in `src/data/states/` exporting a `StateConfig`, adding the code to `StateCode` in `src/types/intake.ts`, adding it to the `state-step.tsx` options, and updating the state lookup in `plan-engine.ts` (currently a `TX ? texas : california` ternary in two places).

## Adding a state: checklist

1. `src/data/states/<code>.ts` exporting `StateConfig` with `code`, `name`, `rules`. Model on `tx.ts`. Cover at minimum: small-estate or simplified-probate path and its threshold and waiting period, what a will changes, creditor notice windows, and any state-specific transfer-on-death or homestead rule.
2. Add the code to `StateCode` in `src/types/intake.ts`.
3. Add the option in `src/components/intake/state-step.tsx`.
4. Import it in `src/lib/plan-engine.ts` and replace the `answers.state === "TX" ? texas : california` ternaries with a lookup keyed by state code (there are two, in `buildPlan` and `buildGatheringPlan`).
5. Optionally add a demo scenario in `src/data/scenarios.ts`.
6. `bun run typecheck && bun run build`.

Cite the statute or an official source in a comment next to any dollar threshold or day count. Thresholds change; the comment is how the next person knows where to check.

## Copy and tone

This product is read by people in the worst week of their lives, often aged 45 to 65, on a phone. The copy rules matter as much as the code:

- Calm, plain, specific. Short sentences. One idea each. Say the plain thing.
- Positive statements. Prefer "you can wait on this" over "don't do this yet".
- Every number has a source or a hedge ("roughly", "in most states"). No invented figures.
- Guidance, never vendor recommendations. Describe what a fair price looks like and what someone is entitled to ask; never name a provider or link to a marketplace.
- No em dashes in product copy. Use commas, periods, or "to" for ranges. No "not X, but Y" contrast framing, no rhetorical questions, no taglines or aphorisms, no exclamation points.
- Care language over task language where they conflict. "It can wait" is a real section with the same weight as the to-dos; respect that.
- Never store or ask for passwords, account numbers, or credentials. The inventory stores where access lives and how to get it, not the secrets.

## Things not to do

- Don't add a backend, auth, or any network dependency to the plan flow. The prototype's premise is that it works with nothing else running.
- Don't add vendor referrals, sponsored placement, or affiliate links.
- Don't put a personal API key anywhere in `src/`. Only a public PostHog project key (`phc_...`) belongs in `analytics.ts`.
- Don't edit `routeTree.gen.ts` or `bun.lock` by hand.
- Don't change the `account_id` in `wrangler.jsonc` unless you're deliberately deploying to a different Cloudflare account.

## Definition of done

`bun run typecheck` clean, `bun run build` succeeds, and the change is visible at `localhost:3000` on both a phone-width and a desktop-width viewport. If you added a rule, load a demo scenario that triggers it and confirm it renders in the right phase.
